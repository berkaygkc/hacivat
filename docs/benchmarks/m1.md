| Settings search → palette (debug build), Japanese | `HACIVAT_DEBUG_FOCUS_MOVE_MS=3000`; compose `kanji`, do not commit, wait | Focus moves to the palette; no stranded candidate window, no stuck underline | **First run FAILED:** the IME candidate window stayed open, stranded above the palette; the palette input was empty. **Re-test after the fix: as expected.** | **PASS** (after fix) |
| Any field, Japanese | Click a menu-bar item while composing | Known behaviour (T16): the click is ignored while composing | Not separately exercised | Open (O-IME2) |

**Root cause of the failed run.** GPUI sends `TextInputStateChange::FocusLost` only on Some↔None transitions of the focused text input. An input→input move (Some(a)→Some(b)) sent nothing, so the carried `discardMarkedText` patch never ran. **Fix:** a second fork commit, `a1eaa20` on the fork branch `hacivat/912159c`, sends FocusLost then FocusGained on an a→b move. The pin moved in `af1ad93` (merged as `61f2ea1`). GPUI and app tests were added and were red without the fix.

Automated coverage: `bindings_do_not_fire_while_composing` (palette) and `bindings_do_not_fire_while_composing_in_settings_search` (cross_surface).
